# PH6-T12 — Đóng gói API/service thành MCP tools

**Status:** not_started. **Phase:** PH6 mở rộng. **Nhóm backlog:** B-018.
**Phạm vi hiện tại:** đặc tả task, chưa tạo hoặc kết nối MCP server mới.

## 1. Kết quả cần đạt

AI client có thể khám phá và gọi các khả năng Builder/API đã chọn qua MCP, dùng cùng service logic, schema và quyền như API hiện có. Đây là adapter protocol; không viết lại Builder bằng một engine khác.

MCP không tự lưu tiến độ coding giữa Codex/Antigravity. Việc đó thuộc harness/checkpoint; CodeGraph phục vụ truy xuất source. Ba chức năng không thay thế nhau.

## 2. Các trường hợp cần phân biệt

| Trường hợp                                                          | Hướng làm trong task                                                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Builder APIs: tạo session, gửi yêu cầu, compile/test draft          | Tạo MCP facade cho các Builder services đã ổn định                                                      |
| API nghiệp vụ đã đăng ký: tra đơn hàng, truy vấn dữ liệu theo quyền | Tái sử dụng connector registry/operation schema; expose capability được chọn, không generic gọi mọi URL |
| Agent/flow Flowise đã có, muốn AI client gọi như tool               | Khảo sát phần MCP theo flow sẵn có để tái sử dụng trước khi viết mới                                    |

Source đã xác minh có routes `packages/server/src/routes/mcp-server/index.ts` quản lý cấu hình theo flow và `packages/server/src/routes/mcp-endpoint/index.ts` nhận MCP messages theo chatflowId. Chúng chưa chứng minh mọi Builder/REST API đã được bọc MCP. Phiên này chỉ đọc source route, chưa thử runtime/auth/compatibility.

Nếu yêu cầu là “mọi API bất kỳ đều chuyển thành MCP”, cần thêm thiết kế import OpenAPI/registry/mapping/error/auth và kiểm thử từng operation. Task này không hứa tự chuyển mọi API chưa biết thành tool hoạt động ngay.

## 3. Phụ thuộc và vị trí trong roadmap

-   Builder API/service muốn expose phải có schema, quyền, error contract và tests.
-   Tool đọc thông tin có thể spike sau PH2; tool build/test cần job/idempotency/cancellation; publish tool cần authenticated approval flow ở PH6-T09.
-   API nghiệp vụ phụ thuộc PH6-T01–T04 hoặc connector tương ứng; SQL vẫn cần controlled executor PH6-T05–T08.
-   Mặc định giữ task ở PH6 để không chặn chat demo. Nếu external AI client là đầu ra bắt buộc của MVP, có thể đưa tập tool nhỏ lên sớm sau PH2/PH3 khi yêu cầu được chốt.

## 4. Tool catalog dự kiến — tên thiết kế, chưa có tool đang chạy

| Tool dự kiến             | Service/API bên dưới      | Giới hạn                                                     |
| ------------------------ | ------------------------- | ------------------------------------------------------------ |
| `builder_list_templates` | Template registry         | Chỉ template actor được phép dùng; metadata ngắn             |
| `builder_get_session`    | Session snapshot          | Scope actor/workspace; không trả toàn transcript mặc định    |
| `builder_send_message`   | Message/collector service | clientMessageId + revision; có thể tạo job, không đợi vô hạn |
| `builder_compile_draft`  | Build/compile service     | buildKey idempotent; trả jobId/revision                      |
| `builder_get_build`      | Job status/result         | Poll theo jobId có quyền; kết quả có giới hạn                |
| `builder_validate_draft` | Validation service        | Kiểm tra đúng revision; lỗi có code, không raw secrets       |
| `builder_run_tests`      | Controlled test service   | Budget, connection quyền và cancellation                     |
| `builder_list_revisions` | Revision store            | Phân trang, summary/diff có giới hạn                         |

Tập tool tối thiểu được chọn theo use case, không bật toàn bộ catalog mặc định. Tool gọi API nghiệp vụ có tên và schema theo operation đã đăng ký; không dùng một `call_any_url` có quyền rộng. Publish chỉ expose khi approval/policy đã có và được kiểm thử, không cho model tự approve.

## 5. Các bước bên trong work package này

1. Inventory API/services và MCP theo flow hiện có; xác định phần nào dùng lại được.
2. Chọn use case/tool subset; mapping method/operation → tool và phân loại quyền/tác động.
3. Pin SDK/protocol/transport phù hợp client và baseline. Remote hoặc local là quyết định theo deployment; không đoán client nào cũng hỗ trợ cùng một version.
4. Xác định input/output schemas, pagination, output caps và error codes.
5. Thiết kế auth context/credential resolution ở server; mỗi tool thực thi quyền của caller theo service hiện có.
6. Implement adapter gọi service nội bộ nếu cùng process; nếu tách deployment thì dùng API client có scope, không gọi vòng HTTP không cần thiết.
7. Tích hợp idempotency/job/cancel cho build/test; không expose một RPC blocking không có giới hạn.
8. Thêm contract/negative tests và smoke test với client được chọn.
9. Viết cấu hình kết nối ví dụ đã bỏ secrets, compatibility notes và hướng dẫn vận hành.

Các bước trên là checklist triển khai của **một task PH6-T12**; không cộng thêm vào tổng 76 task ở root plan. Có thể phân nhỏ khi bắt đầu nếu phạm vi thực tế quá lớn.

## 6. Definition of done

-   [ ] Client thực tế initialize và thấy đúng subset qua `tools/list`.
-   [ ] `tools/call` đi đến đúng service/API và trả output/error theo schema thiết kế.
-   [ ] Sai actor/workspace/quyền bị từ chối; không nâng quyền nhờ gọi qua MCP.
-   [ ] Credential/model key không vào tool args/output/log công khai.
-   [ ] Retry build/test không tạo draft trùng; caller lấy được trạng thái job đúng revision.
-   [ ] Tool output có giới hạn; không dump source, history hoặc catalog khổng lồ vào context.
-   [ ] API operation chưa được đăng ký/không đúng schema không được gọi như một URL tùy ý.
-   [ ] Có runtime smoke test cho client và phiên bản transport được hỗ trợ.
-   [ ] Tài liệu nêu rõ tool đã có, tool chưa có và authorization/publish prerequisites.

Không coi việc viết một JSON config hoặc schema là đã đóng gói MCP thành công. Cần có server/adapter thực thi và client integration test.

Nguồn protocol: [MCP server concepts](https://modelcontextprotocol.io/docs/learn/server-concepts) mô tả tools/resources/prompts và discovery/call. Đây là tham khảo thiết kế; không tự nâng phiên bản MCP đang nằm trong Flowise.
